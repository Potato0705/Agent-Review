# 模型辅助等义改写设计

状态：已批准，待实现
日期：2026-09-21
对应路线图：`variant_generation_design.md` 第 7 节遗留项

## 1. 为什么要做这一项

在已有的真实运行中，等义改写是**唯一持续暴露评分器失效**的变体类型：

| 变体类型 | 违规 / 总数（四轮 Gemma 运行合计） |
|---|---|
| `gaming` | 0 / 17 |
| `degradation` | 3 / 17 |
| `paraphrase` | **7 / 17** |

而抓到这些失效的是**真正的重写**，不是换个连接词。人工改写与基准的位置级重合度只有 0–4%（句式与用词全换、意思不变），规则改写在 `school_start` 上只改了 2 个字。

结论：规则改写几乎不可能复现那些发现，而能自动产出那种强度的改写只有模型或人。这一项不是锦上添花，而是对目前唯一有诊断力的变体类型的自动化。

## 2. 核心危险

1. **循环论证**：生成器与评分器同源时，「什么算等义」由被测系统自己定义。
2. **等义无法机器证明**：规则改写有精确后置条件（剥离连接词后两串完全相等），模型改写没有任何等价物。
3. **客户原文外发**：这是继评分之后的第二条外发链路。

第 2 点决定了工具的姿态：**模型起草，人工批准**。工具绝不为一个它无法验证的等义声明背书。

## 3. 架构约束

`generate` 目前是纯离线、确定性、零依赖的。改写必须是**独立子命令**，不得把模型调用塞进 `generate`，否则会毁掉这个性质。

## 4. 阶段一：起草与审阅

### 4.1 命令

```powershell
python -m agent_audit paraphrase `
  --input examples/essay_baselines.csv `
  --output outputs/paraphrase_review.csv `
  --model YOUR_MODEL `
  --base-url https://YOUR_PROVIDER/v1 `
  --language chinese `
  --temperature 0
```

该命令**只写待审文件，绝不触碰 cases CSV**。输出文件已存在时拒绝覆盖，与 `generate` 一致。

### 4.2 提示词约束

改写提示只包含原文与「保持含义不变地重写」的指令。**绝不包含**：

- 评分标准（rubric）——否则改写会针对被测的评分维度做优化，这是从侧门进来的循环论证；
- 「这是用来测试评分器的」之类的用途说明——会诱导模型产出对抗性而非忠实的改写；
- 任何变体类型标签。

### 4.3 待审文件格式

| 列 | 用途 |
|---|---|
| `case_id` | |
| `baseline_sha256` | 该行所依据的基准文本哈希 |
| `baseline_text` | 并列展示，便于逐条核对 |
| `draft_text` | 模型产出；审阅者可直接修改 |
| `status` | `pending` / `blocked` / `approved` / `rejected` |
| `blocking_checks` | 触发硬拦的检查名，`status=blocked` 时非空 |
| `review_notes` | 机器列出的待核对差异（不影响 status） |
| `reviewer_note` | 审阅者自己的判断记录 |

### 4.4 机器检查：闸门与提示分离

**硬拦**（`status=blocked`，须修改后才能批准）：

| 检查 | 判据 |
|---|---|
| 非空 | 草稿去空白后非空 |
| 非原样 | 草稿 ≠ 基准 |
| 未内含基准 | 基准全文不是草稿的子串（模型回显原文加寒暄） |
| 长度带 | 0.4 ≤ len(草稿)/len(基准) ≤ 2.5 |

实测：五个人工撰写的真·等义改写全部通过，误拦 0/5。

**仅列出供核对**（写入 `review_notes`，不影响 `status`）：

| 提示 | 说明 |
|---|---|
| 基准中出现而草稿中未找到的数字 | 引导注意力到证据句 |
| 否定词计数变化 | 引导注意力到可能的意思翻转 |

这两项**不得做成闸门**。实测中它们会拦下 2/5 的真·等义改写：

- `school_start`：基准「睡眠**不**足」与改写「缺乏睡眠」是同义词，一个含否定字一个不含；
- `campus_phones`：所谓「丢失的数字『一』」其实是「统**一**收纳」里的一。中文没有词边界，数字字符大量出现在普通词中。

40% 的误拦率会训练审阅者直接忽略 `status` 列，比没有检查更糟。

### 4.5 可追溯性

- API 密钥只从环境变量读取；非本机端点必须 HTTPS（沿用既有规则）；
- 默认 `--temperature 0`；
- 待审文件旁生成 `.manifest.json`，记录模型、端点、温度、基准文件哈希、逐行的模型原始回复与调用延迟；
- 命令在 stderr 明确警告：客户原文正在发送给模型供应商；
- 待审文件含客户原文与草稿，按敏感数据处理，`outputs/` 默认不进 Git。

### 4.6 需要动的既有代码

`provider.py` 中的重试、URL 校验与错误处理目前埋在 `OpenAICompatibleScorer.score` 内部。改写器需要复用同一套传输逻辑，因此把传输层抽出为共用函数，评分器与改写器各自只负责解析自己的响应格式。这是对已测代码的重构，由现有传输层测试与变异体兜底。

## 5. 阶段二：批准行入集

### 5.1 命令

```powershell
python -m agent_audit generate --input baselines.csv --output cases.csv `
  --append --paraphrase-review outputs/paraphrase_review.csv
```

只取 `status=approved` 的行。

### 5.2 失败关闭规则

- `status` 出现四个允许值以外的内容即报错。只取 `approved` 而静默跳过拼错的值，会让你以为批准了 5 条实际入集 4 条；
- 某行的 `baseline_sha256` 与当前基准文件中该案例的哈希不一致即报错并指名案例。基准被编辑后，旧草稿对应的是旧文本，混入新案例集会静默产生错误变体；
- 合并后打印 approved / pending / blocked / rejected 四类计数。

### 5.3 来源与循环论证

- 批准行是**人工批准**而非工具可验证生成，因此集合标 `mixed`，审计随即拒绝 `machine-generated`——复用既有机制，不引入新概念；
- 生成清单记录 `paraphrase_model`；审计时与评分清单的 `model` 比对，**完全相同直接拒绝**；
- 报告并列印出改写模型与评分模型。同族不同版本（如 gemma3 改写、gemma4 评分）无法可靠检测，该部分只能交给读者判断，工具不假装有保证。

## 6. 质量门增补

扩充 Gate 11：

- 模型改写只能作为**草稿**进入待审文件，不得直接进入案例集；
- 改写提示不得包含评分标准、用途说明或变体类型标签；
- 只有无歧义的检查可以充当闸门；会对真实等义改写产生误报的检查必须降级为提示；
- 合并时必须校验基准哈希与 `status` 取值，两者任一不合即报错；
- 改写模型与评分模型相同时拒绝审计；报告必须并列两个模型名。

## 7. 明确不做的事

- **不自动判定等义**。没有任何机器检查能证明两段文本意思相同，工具不会声称做到了；
- **不做多候选**。一条草稿加人工编辑已经足够，多候选只增加审阅负担；
- **不把改写结果计为机器生成**。等义的判断来自人，来源标记必须如实反映这一点。
