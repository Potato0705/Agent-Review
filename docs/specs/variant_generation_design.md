# 自动变体生成设计

状态：已实现（v0.9.0 阶段一，v0.10.0 阶段二）
日期：2026-09-21
对应路线图：第7–9周「形成复用资产 / 将重复步骤自动化」

## 1. 要解决的问题

目前每个案例的 `gaming`、`degradation`、`paraphrase` 变体全部手写，是一次交付里最耗时的一步。本设计把其中**干预方式是机械的**部分自动化，并把自动化带来的效力风险显式约束住。

## 2. 核心风险与总原则

自动生成变体对一个审计工具是高风险功能，因为工具的全部效力都建立在「变体确实属于它声称的类别」之上。本设计据此确立三条原则：

1. **机器生成的变体是下限测试。** 追加固定填充句、删除被标注的整句，都是边界清晰、易于抵抗的干预；真实世界的作弊与退化要隐蔽得多。因此**没通过是确凿证据，通过了说明不了什么**。报告必须写明这一点，否则可以用自动变体产出一份高估可靠性的报告。
2. **不确定就拒绝，不猜。** 缺少标注、标注越界、后置条件不成立时一律报错退出，不产出可疑变体。
3. **不加入几乎必然通过的变体。** 违规率的分母是变体总数，掺入一个近乎必然「通过」的变体，等于系统性地把风险评低。这是 `paraphrase` 默认不生成的原因（见 5.4）。

## 3. 不做什么

- **不做关键词堆砌变体。** 中文提取显著词需要分词器；做不准就会产出名不副实的变体，宁可不做。
- **不在 `score` 中边生成边评分。** 变体文本必须是可见、可复核、可手工替换的中间产物，这是 Gate 5 人工复核的前提。
- **不做英文规则。** 第一版只实现中文，但分句与语料通过可替换接口隔离，后续新增实现即可。
- **不把生成清单的内容塞进审计 JSON。** 审计只承载一个来源声明（阶段一），完整的逐变体生成记录留在生成清单里。

## 4. 阶段一：变体来源声明

必须先于生成器落地。否则会出现一个窗口期：生成功能已可用，而报告还无法声明来源——正是原则 1 要防的高估漏洞。

### 4.1 配置字段

`AuditConfig` 增加 `variant_origin`，取值限定为：

| 取值 | 含义 |
|---|---|
| `human-authored` | 全部变体由人工撰写 |
| `machine-generated` | 全部变体由 `generate` 产生 |
| `mixed` | 两者混合 |
| `unspecified` | 未声明（默认） |

非法取值在 `AuditConfig.validate()` 中拒绝，与现有 `data_provenance` 完全同构。

### 4.2 报告渲染

Markdown 与 HTML 报告均渲染该声明。取值为 `machine-generated` 或 `mixed` 时，额外输出固定说明：机器生成的变体属于下限测试，未通过是确凿证据，通过不能证明系统可靠。取值为 `unspecified` 时，沿用现有「未声明来源只能作为内部草稿」的措辞风格。

### 4.3 比较器

`compare` 要求参考与候选两侧的 `variant_origin` 完全一致，不一致直接拒绝，实现方式与现有 `data_provenance` 检查相同。否则可以拿人工变体的基准去比机器变体的候选，得出无意义的结论。

**兼容性：** 不修改 `schema_version`。旧审计 JSON 没有该字段，读取为 `None`；两侧都为 `None` 时相等、可比；只有真正不一致才拒绝。已有产物不会失效。

### 4.4 CLI

`audit` 增加 `--variant-origin`，`choices` 与 4.1 一致，默认 `unspecified`。

### 4.5 验证

- `AuditConfig` 拒绝非法取值；
- 四种取值在 Markdown 与 HTML 中都能渲染，且下限测试说明只在 `machine-generated` 与 `mixed` 时出现；
- `compare` 在两侧不一致时拒绝，两侧均缺失时接受；
- 变异体：删除 `variant_origin` 的一致性检查后必须有测试失败。

## 5. 阶段二：`generate` 子命令

### 5.1 数据流

```text
带标注的基准CSV ──generate──> cases CSV + 生成清单
                                    │
                                    ├──score──> 评分CSV + 评分清单
                                    └──audit──> 报告
```

输出的 cases CSV 就是 `score` 现有的输入格式，因此任何一行都可以手工替换后重新喂入，整份也可以弃用。

输出行的 `notes` 采用与评分模块一致的分段格式：`generated=<策略名>; <干预幅度>`，输入带 `notes` 时追加 `| source_note=<原文>`。基准行的 `notes` 为 `generated=baseline`。

### 5.2 输入格式

一行一个案例的最小 CSV：

| 列 | 必填 | 含义 |
|---|---|---|
| `case_id` | 是 | 案例ID，全文件唯一 |
| `text` | 是 | 基准文本，非空 |
| `evidence_sentences` | 是（见 5.6） | 1 起的句序号，逗号分隔，如 `2,3` 或 `2, 3`，标出承重的证据或核心主张。允许空格，每项必须是正整数，顺序不限，不得重复 |
| `notes` | 否 | 案例说明，作为 `source_note=` 并入输出行的 `notes` |

### 5.3 分句契约

中文分句以 `。！？；!?;` 及其后续的引号、括号为界，分隔符归属前一句。

**不变量：`"".join(split(text)) == text`。** 这保证按序号删除是精确的、可陈述的。该不变量在现有 20 个真实案例文本上测试。

分句器与语料封装在可替换的「语言策略」接口后，是后续支持其他语言的唯一扩展点。

### 5.4 变体策略

变体ID固定可预测，保证跨运行稳定，`compare` 才能成立。

**`gaming`（分数不应上升），默认两条全开：**

| 策略 | 变体ID | 干预 |
|---|---|---|
| `verbose_padding` | `gaming_verbose_padding` | 在基准末尾追加 2 句内置语料中的中性无关句 |
| `rubric_flattery` | `gaming_rubric_flattery` | 在基准末尾追加 1 句评分术语与抽象赞美堆砌句 |

追加句数为固定值，第一版不开放配置。语料按种子无放回抽取，同一案例内不重复。

两者直接对应评分标准中明写的约束：「与论点无关的扩写不能提高分数」「重复关键词、评分术语或抽象赞美不能提高分数」。

**`degradation`（分数应下降），默认两条全开：**

| 策略 | 变体ID | 干预 |
|---|---|---|
| `remove_evidence` | `degradation_remove_evidence` | 精确删除标注句 |
| `unsupported_assertion` | `degradation_unsupported_assertion` | 删除标注句，并插入内置语料中的无依据断言句 |

**`paraphrase`（分数应基本不变），默认关闭：**

| 策略 | 变体ID | 干预 |
|---|---|---|
| `connective_substitution` | `paraphrase_connective_substitution` | 按内置对照表替换关联词（因此→所以、此外→另外、但是→然而等） |

默认关闭的理由见原则 3：该改写编辑距离极小，评分器几乎必然给出近似分数，掺入后会稀释违规率并把风险评低。显式 `--paraphrase connective_substitution` 才生成，且该行 `notes` 必须标明它是**弱探针**，不等同于真正的等义改写。真正的改写由人工撰写或后续的可选模型路径提供。

### 5.5 后置条件（不成立即报错退出）

| 策略 | 必须成立 |
|---|---|
| `verbose_padding`、`rubric_flattery` | 输出以完整基准文本为前缀，且严格更长——证明只增不减 |
| `remove_evidence` | 严格更短；每个标注句都不出现在输出中；未标注句按原序完整保留 |
| `unsupported_assertion` | 每个标注句都不出现在输出中；插入的断言句出现在输出中；未标注句按原序完整保留 |
| `connective_substitution` | 与基准不同（非空操作）；**剔除对照表中全部关联词后，两者字符串完全相等** |

最后一条是精确不变量，能证明该改写确实只动了关联词。

### 5.6 失败关闭规则

以下情况报错退出，不产出任何输出文件：

- 启用的策略集合中缺少 gaming 或缺少 degradation。`load_scoring_cases` 要求每个案例同时具备两者，只开一侧会产出无法进入 `score` 的 CSV，因此**必须至少各启用一条**；
- 任一案例缺少 `evidence_sentences`。由于退化策略始终启用（见上条），标注是必填项。错误信息列出全部缺标注的 `case_id`，避免产出无法通过校验的 CSV；
- 句序号越界、重复或非整数；
- 标注覆盖全部句子，删除后将不剩任何内容；
- 基准文本为空，或分句后不足两句——退化必须在删除证据后仍保留内容，单句基准做不到；
- 任一后置条件不成立；
- `case_id` 重复。

### 5.7 生成清单

输出 CSV 旁生成 `.manifest.json`，字段包括：

- 工具版本、生成时间、随机种子；
- 输入文件 SHA-256、案例数、输出行数；
- 启用的策略集合；
- `requires_human_review: true`；
- **逐变体记录**：`case_id`、`variant_id`、策略名、干预幅度（删除字符占比、追加句数、替换关联词数），以及**该案例实际插入的填充句或断言句原文**。

记录原文而非只记策略名，是为了让人工能逐条确认「无关」这一前提在该题目上真的成立——固定语料撞上相近题目时它并不成立。

### 5.8 确定性

`--seed` 控制语料选取，默认 `0`。**同一输入 + 同一种子 → 逐字节相同的输出**，并在清单中记录种子。

### 5.9 CLI

```powershell
python -m agent_audit generate `
  --input examples/essay_baselines.csv `
  --output outputs/generated_cases.csv `
  --manifest outputs/generated_cases.manifest.json `
  --gaming verbose_padding,rubric_flattery `
  --degradation remove_evidence,unsupported_assertion `
  --seed 0
```

`--paraphrase` 省略时不生成改写变体。`--manifest` 省略时默认写在输出 CSV 旁。

### 5.10 模块划分

保持现有扁平结构，不建子包：

- `agent_audit/segmentation.py` — 分句与语言策略接口
- `agent_audit/variants.py` — 策略实现与后置条件
- `agent_audit/io.py` — 增加 `load_baseline_cases` 与 `write_scoring_cases`
- `agent_audit/cli.py` — 增加 `generate` 子命令
- `examples/essay_baselines.csv` — 与现有 20 个案例对应的带标注基准

顺带修复一处潜在漏洞：`scripts/coverage_report.py` 目前只扫 `agent_audit/*.py` 而不递归，新增模块若放进子包会静默不计入覆盖率。改为递归扫描。

### 5.11 验证

- 分句可逆性不变量，覆盖现有全部真实案例文本与边界输入；
- 每条后置条件的红绿验证；
- 确定性：同种子逐字节相同，不同种子产出不同填充；
- 全部失败关闭规则各有用例；
- 端到端：`generate` 的输出能被 `load_scoring_cases` 接受，即可直接进入 `score`；
- 变异体：关闭任一后置条件、放宽任一失败关闭规则后，必须有测试失败。

## 6. 质量门增补

新增 Gate 11「变体生成」：

- 机器生成的变体只能作为下限测试引用，报告必须声明来源；
- 退化变体只能依据人工标注生成，不得由工具推断承重内容；
- 每个变体必须通过其类别的机器可验证后置条件；
- 生成清单必须记录干预幅度与实际插入的语料原文；
- 交付前必须逐条人工确认变体确实符合其类别定义，本门不替代 Gate 5。
