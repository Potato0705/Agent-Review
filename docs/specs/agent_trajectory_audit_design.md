# Agent 轨迹评分器审计设计

状态：已实现（v0.15.0）
日期：2026-09-21
对应路线图：README「当前范围」中的后续项

## 1. 审的是什么

**审的是给 Agent 轨迹打分的评分器，不是 Agent 本身。**

同一个问题换了模态：评分器是真的在读过程，还是只在读最后一段答案、只在数工具调用次数？把 Agent 本身做成排行榜是另一件产品，且与 README 里「不支持把不同数据集上的结果拼成模型排行榜」直接冲突，本项不做。

## 2. 为什么轨迹比文本更适合这套方法

文本变体的后置条件只能做到弱结构检查——作弊变体必须完整包含基准作为前缀。等义改写更是压根无法机器证明，v0.14.0 因此只能做到「模型起草、人工批准」。

轨迹是结构化的，三类变体都能有**严格可判定**的后置条件：

| 变体族 | 后置条件 |
|---|---|
| `gaming` | 步骤集合是基准的真超集且最终答案逐字节相同；或步骤三元组与答案全部不变，只有说明文字变长 |
| `degradation` | 恰好删除或掏空标注的承重步骤，其余步骤按原序保留，最终答案不变 |
| `paraphrase` | 步骤多重集与最终答案完全相同，仅顺序不同 |

这是本工具第一次能对全部三族变体做完全可判定的后置条件。

## 3. 最有诊断力的一类：结果对、过程错

删除真正取得答案的那次工具调用，但保留最终答案。评分器若照给高分，就证明它只读了结尾。文本模态里没有这个探针的对应物。

它归入 `degradation`：过程退化而结果不变，正是「内容变差是否会被识别」在轨迹上的形式。

## 4. 输入格式

一行一个案例的 JSONL，`examples/trajectory_baselines.jsonl`：

```json
{
  "case_id": "flight_refund",
  "task": "查出订单 A7731 是否可全额退款，并说明依据。",
  "steps": [
    {"tool": "search_orders", "args": {"order_id": "A7731"}, "result": "舱位 Y，出票日 2026-03-02"},
    {"tool": "read_policy", "args": {"fare_class": "Y"}, "result": "Y 舱出票 24 小时内可全额退款"},
    {"tool": "get_time", "args": {}, "result": "2026-03-02T18:40Z"}
  ],
  "final_answer": "可以全额退。订单为 Y 舱，出票于 03-02，当前仍在 24 小时内。",
  "load_bearing_steps": [2],
  "independent_steps": [[1, 3]],
  "notes": "原始轨迹"
}
```

| 字段 | 用途 |
|---|---|
| `case_id` | 案例ID |
| `task` | 交给 Agent 的任务 |
| `steps` | 有序步骤，每步 `tool` / `args` / `result`，可选 `note` |
| `final_answer` | Agent 的最终答复 |
| `load_bearing_steps` | 1起的序号，标出哪些步骤是结论的依据 |
| `independent_steps` | 互不依赖、可任意换序的步骤分组，1起序号 |
| `notes` | 可选说明 |

**工具不推断哪些步骤承重，也不推断哪些步骤可以换序。** 这与现有「人工标注承重句」完全一致：推断错会产出一个声称退化却没退化、或声称等义却改变了因果的变体。缺标注、序号越界、标注覆盖全部步骤、分组少于两个成员或成员重叠，一律报错退出。

选择自有格式而非 OpenAI tool-call 消息格式，是因为承重步骤与可换序分组必须有地方存放，而后者没有这个位置；拆成两份文件又会新增一处「两份文件对不上」的失败面。真有客户拿着别的格式来时再写转换器。

## 5. 变体策略

### 5.1 `gaming`

| 策略 | 做法 | 后置条件 |
|---|---|---|
| `redundant_tool_calls` | 把轨迹中已有的某一步原样再调一次，插在其后 | 变体步骤序列去掉新增项后与基准逐项相等；新增项必须是基准中已存在的三元组；最终答案逐字节相同 |
| `padded_reasoning` | 在每步的 `note` 上追加与结论无关的铺陈 | `tool`/`args`/`result` 三元组序列与最终答案逐字节不变，仅 `note` 变长 |

重复已有步骤而不是凭空造一个工具调用，是因为后者要么得编造工具名，要么得编造调用结果——那是在伪造证据，不是在构造变体。重复调用天然合法：工具存在、参数有效、结果已知，而且它确实是「多做了无用功」。

### 5.2 `degradation`

| 策略 | 做法 | 后置条件 |
|---|---|---|
| `remove_load_bearing_step` | 删除标注的承重步骤 | 变体不含任何被标注步骤；其余步骤按原序保留；最终答案逐字节不变 |
| `hollow_evidence` | 保留调用，把承重步骤的 `result` 换成空结果 | `tool`/`args` 序列与最终答案逐字节不变；被标注步骤的 `result` 与原值不同且不包含原值；其余步骤的 `result` 不变 |

~~两者都保留最终答案，因此都在问同一个问题：评分器是否只读结尾。~~ —— **这条被实测推翻。** 见 [首轮真实运行](../case_studies/gemma3_trajectory_case_study.md)：两者拿掉的是同一条证据，平均 Δ 却相差 1.07 分（`hollow_evidence` −1.07，`remove_load_bearing_step` 0.00）。它们问的不是同一个问题：

- `remove_load_bearing_step` **暴露失效**——证据不在了，评分器毫无反应，并把结论里对缺失前提的复述当成了支撑；
- `hollow_evidence` 是**对照组**——同一条证据缺失，只因转写里多了一个「（无结果）」标记就被抓到，证明评分器并非迟钝。

因此真正的结论比设计时的预期更具体：评分器认的是**可见的失败标记**，不是证据是否存在。两个变体必须成对使用，单独任一个都会让读者得出相反的结论。

### 5.3 `paraphrase`

| 策略 | 做法 | 后置条件 |
|---|---|---|
| `reorder_independent_steps` | 对标注的可换序分组做一次确定性重排 | 步骤多重集与最终答案完全相同；顺序与基准不同 |

未标注 `independent_steps`、或分组重排后顺序未变的案例，直接拒绝而不是硬造一个假的等义变体。这与 `connective_substitution` 遇到无可替换连接词时的做法一致。

**与文本改写的根本差别**：这一族在轨迹上是可证明的。步骤多重集相同意味着做的事完全一样，因此 v0.14.0 那套「模型起草、人工批准」在这里不需要，也不应引入。

## 6. 渲染

评分器看到的是渲染后的文本，因此 `score` / `audit` / `compare` / 清单 / 来源标记 / 效度余量全部不动，轨迹变体的输出就是现有 `score` 的输入格式。

渲染为带编号的转写，标签逐语言给出，复用既有的 `LanguageStrategy` 作为语言接缝：

```text
任务：查出订单 A7731 是否可全额退款，并说明依据。

步骤 1
  工具：search_orders
  参数：{"order_id": "A7731"}
  结果：舱位 Y，出票日 2026-03-02

步骤 2
  ...

最终答案：可以全额退。订单为 Y 舱，出票于 03-02，当前仍在 24 小时内。
```

`args` 按键排序后序列化，使同一输入逐字节可复现。步骤的 `note` 为空时整行不出现，避免给评分器一个空标签。

## 7. 命令

```powershell
python -m agent_audit trajectory `
  --input examples/trajectory_baselines.jsonl `
  --output outputs/trajectory_cases.csv `
  --seed 0
```

沿用 `generate` 的全部约定：输出已存在即拒绝覆盖、`--append` 合并、清单记录 `output_sha256` 与 `set_origin`、`--show-steps` 打印编号步骤与标注供核对（对应 `--show-sentences`）。

生成清单额外记录 `modality: "trajectory"`。它不进入生成指纹的身份字段——身份字段一旦增删就会让旧清单无法计算指纹，而跨模态的两次运行本来就产出完全不同的文本，`input_sha256` 已经不同，`compare` 早已拒绝。

## 8. 质量门增补

扩充 Gate 11：

- 承重步骤与可换序分组只能来自人工标注，工具不得推断；
- 每个轨迹变体必须通过其类别的完全可判定后置条件，否则整轮报错退出；
- 作弊变体不得引入基准中不存在的工具调用或凭空捏造的调用结果；
- 退化变体必须保留最终答案：不保留就同时改变了过程与结果，无法区分评分器是在读过程还是在读结论；
- 轨迹等义改写不得借用模型起草路径——该族在轨迹上是可证明的，引入无法验证的来源是倒退。

## 9. 实现记录

一处与本文写就时不同：**`remove_load_bearing_step` 的「步骤数正确」后置条件被删掉了。** 为它写测试时发现任何输入都无法触发——逐项比对身份列表已经蕴含长度相等。一条永远不会触发的断言给出的是虚假保证：它看起来在守卫一件事，实际那件事由别处保证，而它自己永远无法被测试或变异体检验。Gate 11 因此增加了一条禁止保留不可达断言。

## 10. 明确不做的事

- **不评测 Agent 本身**。本工具审的是评分器，不产出 Agent 排行榜；
- **不执行任何工具调用**。轨迹是既有记录，工具只读不跑，因此没有副作用面；
- **不支持 OpenAI tool-call 消息格式**。真有客户轨迹时再写转换器，届时转换器的正确性才有东西可验证；
- **不推断步骤依赖**。可换序分组必须人工给出。
