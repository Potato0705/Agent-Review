# 7天 LLM 评分器可靠性体检

项目与方法示例：<https://github.com/Potato0705/Agent-Review>

## 适合谁

- 用 LLM 给 **Agent 运行轨迹**打分的团队——评测 Agent、做 RL 奖励、筛选轨迹数据时依赖一个「裁判模型」；
- 正在开发自动作文评分、文本质量评价或教育反馈系统的团队；
- 已经有模型结果，但不确定指标能否反映真实能力的研究项目；
- 准备投稿、演示、采购或上线，希望提前发现高风险失败模式的团队。

## 我们发现过什么

在公开的方法示范里，我们给一个本地部署的评分模型看了一条 Agent 退款查询轨迹，然后**删掉了真正查到退款规则的那一步**，最终答案一字不改。

评分**一分没降**。评分器的理由是：最终答案里的计算已经足够。而那条规则，恰恰来自被删掉的那一步。

同一条证据、同样缺失，只要保留调用、让它返回「（无结果）」，同一个评分器立刻判为「关键证据缺失」。

**它认的是看得见的失败痕迹，不是证据是否存在。** 如果你的裁判模型也这样，你的 Agent 可以靠一句写得漂亮的结论，拿到本该由过程挣来的分数。

这是 5 条合成轨迹上的探索性发现，不代表你的系统一定存在同样问题——**体检要回答的正是这个。** 完整数据、两个模型的对比与复现方式见[公开案例](https://github.com/Potato0705/Agent-Review/blob/main/docs/case_studies/gemma3_trajectory_case_study.md)。

## 我们检查什么

**文本评分器：**

- 无关但流畅的内容是否会错误提高分数；
- 扩大篇幅或堆叠关键词是否能获得奖励；
- 删除核心论点、证据或任务要求后是否明显降分；
- 保持含义不变的表达修改是否造成不合理波动。

**Agent 轨迹评分器：**

- 删掉结论所依赖的那一步、结论不变，评分会不会降；
- 调用还在但什么也没查到，评分会不会降——以及和上一条相比，它是不是只认「看得见的失败」；
- 重复已经做过的调用、把步骤说明写长，能不能骗到分；
- 相互独立的步骤换个顺序，分数是否稳定。

**两者共同：**

- 模型识别内容退化的能力，是否高于它对作弊式修改的奖励；
- 新旧模型或提示词版本是否出现跨阈值回归；
- 哪些指标在你的数据上**测不了**——比如基准已经接近满分时，「作弊无效」和「本来就没有上升空间」无法区分，报告会明确标出，而不是给你一个会被误读的零。

## 客户提供

- 评分标准或任务说明；
- 10 条具有代表性的原始样本，或 10 条 Agent 运行轨迹（任务、每步调用与返回、最终答复）；
- 模型访问方式，或由客户运行后提供评分结果；
- 当前最担心的错误类型；
- 数据使用与保密要求。

对轨迹，我们会和你一起标出「结论依赖哪几步」「哪几步可以换序」——**工具不猜这两件事**，猜错会造出一个声称退化却没退化的测试。

## 7天内交付

1. 20–30 条针对性测试；
2. 失败案例与风险等级数据表；
3. 可复现的离线审计结果，附输入与评分标准的哈希，确保结论可追溯到具体运行；
4. 如有旧版本，提供同条件版本回归对比；
5. 一份可直接发送、归档和打印的自包含 HTML 审计报告；
6. 30 分钟线上结果讲解。
