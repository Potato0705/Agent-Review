# 质量审查门

Agent Review 的功能不能仅以“命令能够运行”为完成标准。每一阶段必须通过以下审查门。

## Gate 1：数据与配置

- 输入字段齐全且非空；
- 每个案例只有一个基准；
- 每个案例同时包含作弊与内容退化对照；
- ID唯一，分数有限并处于声明范围；
- 阈值非负且与评分量表一致。

## Gate 2：逻辑不变量

- 作弊收益始终定义为 `变体分 − 基准分`；
- 退化降分始终定义为 `基准分 − 变体分`；
- 等义波动取绝对差；
- 效度余量始终定义为 `平均退化降分 − 最大正向作弊收益`；
- 变体标签不能发送给被测评分模型；
- 少于5个基准案例只能声称演示级发现，5–29个只能声称探索性发现；30个以上也只是筛查级。
- 重复采样使用样本标准差；小样本临界判定使用保守95% t 区间；
- 不确定性未完整覆盖或区间跨越阈值时，风险等级必须标为暂定。

## Gate 3：安全与可追溯

- API密钥不出现在参数、CSV、JSON、日志或Git历史中；
- 远程端点必须使用HTTPS；
- 运行清单记录模型、端点、温度、输入哈希和评分标准哈希；
- 原始响应默认不保存；
- `outputs/` 中的评分CSV、报告、清单与原始JSONL默认不进入Git；
- 客户数据必须获得授权，并遵循保存与删除要求。

## Gate 4：自动化验证

- `python -m compileall -q agent_audit tests` 通过；
- `python -m unittest discover -s tests -v` 通过；
- `python scripts/coverage_report.py` 通过，且没有模块跌破其棘轮下限；
- `python scripts/mutation_check.py` 通过，全部变异体均被测试捕获；
- 新增拒绝分支必须同时有用例与变异体；仅有用例而变异体存活，说明该用例可能凭错误原因通过；
- 离线演示能生成Markdown与JSON；
- OpenAI-compatible本地模拟端到端测试通过；
- 重复采样的聚合记录数、原始轨迹数和清单重复次数相互一致；
- 故障注入后只恢复缺失样本，已完成调用不重复；
- 检查点上下文不匹配、重复键和已换行畸形记录必须失败关闭；
- 新运行不能覆盖已有检查点，末尾修复只能发生在完整验证之后；
- `git diff --check` 无空白错误；
- `git diff --cached --check` 无已暂存文件的空白错误；
- GitHub Actions在Python 3.10和3.12通过，并在推送后逐次确认，而不是假定本地通过即等同于CI通过；
- 覆盖率预算必须在最低受支持的解释器上成立；不同版本对可执行行的归属存在一两行差异。

## Gate 5：人工结论审查

真实客户报告发布前必须逐项确认：

- 每个测试变体是否真的符合其类别定义；
- 评分变化是否具有业务意义，而不只是统计差异；
- 高风险案例是否能稳定复现；
- 建议是否由证据支持；
- 报告是否明确没有测试的内容；
- 是否错误地把“未发现问题”写成“系统可靠”。

## Gate 6：版本对比

- 参考与候选结果的案例、变体类型、阈值和量表完全一致；
- 输入哈希、评分标准哈希、温度和重复次数有评分清单证据且完全一致；
- 数据来源声明一致；
- 正向严重度变化在三类变体中都表示候选系统变差；
- 跨阈值变化与阈值内幅度变化分开报告；
- 任一侧未估计不确定性或属于临界判定时，变化标为暂定；
- 不把描述性差异写成统计显著差异或总体模型排名。

## Gate 7：长任务恢复

- 每个成功样本在下一次调用前完成持久化；
- 恢复后的 `run_id`、输入哈希和评分标准哈希保持不变；
- 恢复结果与未中断结果的聚合CSV一致；
- 清单分别记录恢复样本数、新调用数、延迟和令牌汇总；
- 检查点按敏感数据处理，且不进入Git。

## Gate 8：HTML交付

- 所有来自输入、模型或清单的不可信文本在进入HTML前完成转义；
- 页面不包含可执行脚本、外部字体或外部网络资源，并设置限制性内容安全策略；
- 审计与版本对比的核心指标、发现、上下文和限制与结构化结果一致；
- 桌面与移动视口均完成浏览器复核，无控制台错误或页面级横向溢出；
- 窄屏详细表格保持可读最小宽度，并在局部容器内横向滚动；
- 打印样式不依赖屏幕背景或阴影表达关键信息。

## Gate 9：公开资产与仓库治理

- 文档按示例、真实案例、服务、作品集和治理分类，并由 `docs/README.md` 统一导航；
- 提交的HTML示例只能来自合成或明确可公开数据，并能由仓库脚本确定性重建；
- 自动测试验证公开HTML与当前渲染器一致，所有相对Markdown链接指向现存文件；
- 自动测试验证公开需求模板链接指向现存模板文件，且 `docs/` 中没有游离于导航之外的文档；
- 公开数字主张与当前结构化结果一致，并同时说明样本量、证据等级和不能支持的结论；
- 公开需求入口明确禁止提交密钥、私有样本、个人信息和保密材料；
- `outputs/`、浏览器证据和自动化临时状态均保持忽略，跟踪文件不存在异常大文件或凭据类文件；
- 全部提交和标签只使用仓库所有者身份，不包含其他作者、提交者或共同作者Trailer；
- 推送后本地与远端分支、版本标签的目标提交完全一致。

## Gate 10：测量正确性

本工具的交付物是一个测量结论，因此实现正确性本身就是安全边界，不能只靠「命令跑通」和示例测试。

- 公布的公式必须有独立重演的属性测试：由文档定义重新推导效度余量与违规计数，在随机输入上与实现逐项比对；
- 三类判定的阈值边界必须有显式测试；落在阈值上的变体一律不算违规，与README的「上升」「不足」「超过」一致；
- 分数必须在进入任何比较前验证为有限值；比较运算对NaN恒为假，未经检查的NaN会把结论反转为「无违规」；
- 重复采样的临界值在超出t表范围后必须保持最保守取值，不得改用正态近似；
- 来自模型的输出按不可信输入处理：布尔值、字符串、数组、代码块和夹杂散文都必须有明确的接受或拒绝行为；
- 新增或修改判定逻辑时，必须在 `scripts/mutation_check.py` 中登记对应变异体；无法被任何测试捕获的变异体等同于没有测试；
- 只有在被变异体针对的代码本身被删除时，才允许移除该变异体；不得为使门禁转绿而删除；
- 断言必须定位到计算结果本身；报告中同时列出全部等级名称的静态说明句，不能用作等级判定的证据。

## Gate 11：变体来源

- 报告必须声明变体由人工撰写、工具生成还是混合产生；
- 机器生成的变体只能作为下限测试引用：未通过是确凿证据，通过不能证明系统可靠；
- 版本对比要求两侧的变体来源声明完全一致；
- 来源未声明的报告与数据来源未声明同等对待，只能作为内部草稿。

## 发布条件

只有Gate 1–4、Gate 9、Gate 10和Gate 11全部通过，才能发布基础代码版本；包含版本对比时还必须通过Gate 6，启用检查点时还必须通过Gate 7，交付HTML时还必须通过Gate 8。只有Gate 1–5全部通过，才能交付真实客户报告。
