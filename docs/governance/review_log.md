# 审查日志

本文件记录每一阶段发现的逻辑风险、修改和验证证据。新增功能必须经过至少一次实现审查和一次回归审查。

## 审查门A：离线MVP

### 发现的问题

1. 输入允许 `NaN` 或无穷分数，可能污染平均值和风险等级；
2. 同一案例允许重复 `variant_id`，报告可能无法唯一追溯测试；
3. 小样本报告没有提醒证据不足，低风险可能被误读；
4. 评分量表没有边界，0–5和0–100分可能误用同一阈值；
5. 配置允许负容忍值等无效参数。
6. 即使声明了0–5或0–100量表，严重风险阈值仍固定为2分和反向1分，会产生单位依赖误判。

### 修复

- 拒绝非有限分数和重复变体ID；
- 增加可选 `score_min`、`score_max` 边界；
- 所有阈值必须有限且非负；
- 少于5个基准案例时标记为演示级，5–29个为探索性，30个以上为筛查级；
- README明确默认阈值按0–10分量表设计。
- 声明评分范围后，严重风险阈值按量表跨度20%和10%自动缩放。

### 验证

- 单元测试覆盖高风险、低风险、重复ID、缺少基准、负阈值和越界分数；
- 合成示例继续产生高风险、66.7%违规率和-0.63平均效度余量。
- 跨量表测试验证0–5与0–100量表不会错误共用固定严重阈值。

## 审查门B：真实模型接入

### 设计风险

1. API密钥可能进入命令历史、日志或运行清单；
2. HTTP传输可能泄露客户文本；
3. 把 `gaming` 等变体标签告诉评分模型会造成实验泄漏；
4. 模型可能返回代码块、畸形JSON、越界分数或非有限数；
5. 只有作弊测试、没有内容退化对照时，不能解释效度余量；
6. 模型版本和评分标准变化后，结果可能不可追溯。

### 修复

- 密钥只从指定环境变量读取，不进入配置清单；
- 除localhost和127.0.0.1外，所有端点必须使用HTTPS；
- 评分请求只包含评分标准和待评分文本，不传变体类型；
- 严格解析JSON并校验分数范围；
- 每个案例强制包含一个基准、至少一个作弊和一个退化变体；
- 保存模型、端点、温度、输入哈希、评分标准哈希和响应ID；
- 原始回复仅在显式指定 `--raw-output` 时保存。

### 验证

- 本地HTTP模拟器验证OpenAI-compatible请求路径、授权头、代码块JSON解析和usage读取；
- 测试确认请求中不包含 `gaming` 或 `degradation` 标签；
- 端到端测试覆盖案例CSV → 模型评分 → 评分CSV → 离线审计 → 清单与原始追踪文件；
- CI在Python 3.10和3.12运行编译、测试和离线演示。

## 尚未关闭的风险

- 当前风险等级是透明的启发式规则，还没有用真实客户结果校准；
- 当前只评估数值评分，不评估完整Agent工具调用轨迹；
- 仍需使用更多基准案例和重复采样，才能把公开示范升级为正式证据。

## 审查门C：首个真实本地模型示范

### 执行

- 使用本机Ollama的 `gemma3:4b`；
- 使用项目自带的8条公开示范文本和0–10分评分标准；
- 温度为0，保存运行清单和显式启用的原始响应；
- 不向本地服务发送已存在的OpenAI密钥。

### 发现的问题

自动报告无条件声称输入是“合成演示”，导致真实本地模型结果被错误标记。

### 修复

- 增加 `data_provenance` 配置；
- 区分 `synthetic`、`public-demo`、`authorized-private` 和 `unspecified`；
- 来源未声明时在报告中明确警告，正式交付必须补充来源与授权。

### 初步结果

- 扩展到5个基准案例、15个变体后，综合风险由演示级的高调整为探索性的中；
- 15个变体测试中4个违规；
- 5个等义改写中3个产生1分波动；
- 一个内容退化样本没有降分；
- 所有作弊式修改均未获得正向奖励；
- 结果仍只有5个手工基准案例，严格标记为探索性，不能外推总体可靠性。

## 审查门D：重复采样与不确定性

### 设计风险

1. 固定使用正态分布的1.96临界值会低估3次等小样本的不确定性；
2. 聚合评分只保留一个理由时，可能被误读为全部样本理由一致；
3. 风险等级按均值计算时，LOW与多项临界判定同时出现，容易被误解为稳定低风险；
4. 输出目录原先只忽略Markdown和JSON，评分CSV与原始JSONL可能被误提交。

### 修复

- 使用样本标准差与均值差标准误；
- 使用保守95% t 区间，自由度取两组中较小样本量减1；
- 聚合CSV把理由明确标为 `sample_1_reason`，全部理由保存在显式启用的原始轨迹中；
- 增加不确定性覆盖数；覆盖不足或存在临界项时，风险等级标为“暂定”；
- 默认忽略 `outputs/` 下所有生成文件，只保留 `.gitkeep`。

### 验证

- 20项自动化测试覆盖小样本t区间、重复采样聚合、CSV往返、暂定风险和端到端轨迹数量；
- 对5个基准案例执行每条3次评分，共20条聚合记录和60条原始轨迹；
- 清单记录 `repeats=3`，每个分组恰好有3条轨迹；
- 15项变体全部覆盖不确定性，5项区间跨越阈值，报告为LOW（暂定）；
- 人工逐项核对三次原始得分、均值、样本标准差和判定方向。

## 审查门E：模型与版本对比

### 设计风险

1. 不同案例、阈值或量表的结果可能被错误拼接成模型排名；
2. 作弊、退化和改写三类差值方向不同，直接相减容易颠倒“变好/变差”；
3. 按均值从违规变为不违规时，若区间仍跨阈值，不能宣称稳定改善；
4. `AuditResult.to_dict()` 在内存中保留元组，写入JSON后变为数组，曾导致内存对象与落盘对象行为不一致。
5. 仅核对相同案例ID不能证明两次运行使用了相同输入文本、评分标准、温度和重复次数。

### 修复

- 强制两侧案例/变体身份、变体类型、阈值和评分范围一致；
- 将三类变体统一换算为“严重度增加表示候选变差”；
- 分开报告跨阈值回归、跨阈值改善和阈值内幅度变化；
- 任一侧缺少标准误或属于临界判定时，将变化标为暂定；
- 比较器同时接受内存元组与JSON数组，并增加对应回归测试。
- 审计JSON自动读取相邻评分清单，保存输入哈希、评分标准哈希、温度和重复次数；缺少或不一致时拒绝比较。

### 验证

- 10项比较测试覆盖回归、改善、阈值不兼容、来源声明、案例不一致、schema、摘要一致性、运行指纹和CLI端到端输出；
- Gemma 3 4B与Gemma 4 E4B各产生20条聚合记录和60条原始轨迹；
- 两侧输入哈希、评分标准哈希、温度和重复次数完全一致；
- 对比得到0项跨阈值回归、3项跨阈值改善，但3项改善均标为暂定；
- 15项变化中10项涉及至少一侧临界判定，未据此声称候选模型总体胜出。

## 审查门F：长任务检查点与恢复

### 设计风险

1. 长时间评分在末尾失败时，已完成调用全部丢失并产生重复费用；
2. 新运行可能静默覆盖旧检查点；
3. 错误输入、评分标准、模型或采样参数可能误用旧结果；
4. 自动修复末尾残缺JSON时，若尚未确认运行上下文，可能修改不属于本任务的文件；
5. 检查点保存完整模型回复，敏感程度不低于原始轨迹；
6. 只记录总耗时无法区分真实模型调用与快速恢复。

### 修复

- 每个成功样本在发起下一次调用前追加到JSONL，并刷新到磁盘；
- 新运行使用独占创建，已存在时必须显式 `--resume`；
- 检查点绑定系统名、供应商、模型、端点、量表、温度、重复次数及双哈希；
- 先验证头部、上下文、所有完整样本和重复键，再修剪唯一允许恢复的未换行末尾片段；
- CLI明确警告检查点包含完整回复，所有 `outputs/` 产物继续默认忽略；
- 清单分别记录恢复样本、新调用、调用延迟、墙钟时间和完整令牌汇总。

### 验证

- 7项故障注入测试覆盖中断后续跑、上下文不匹配、样本语义不匹配、拒绝覆盖、末尾安全修复、已换行畸形记录和无效供应商结果；
- 测试确认上下文不匹配时，即使文件带残缺尾部也不会被修改；
- 本地Gemma 3首轮完成20次调用，检查点包含1条头部和20条样本；
- 第二次恢复复用同一 `run_id`，恢复20条、新调用0条，墙钟时间约0.018秒；
- 恢复前后评分CSV的SHA-256完全一致；
- 清单汇总7969个提示令牌、1887个完成令牌和约46.98秒样本调用延迟。

## 审查门I：测量正确性专项审计

本轮不新增功能，只审查已发布实现是否真的计算了文档承诺的东西，并把审查手段固化为可重复门禁。

### 发现的缺陷

1. **非有限分数失败打开。** `audit_records` 是公开API，却只校验 `sample_count` 与 `score_stddev`，不校验分数本身。仅当声明评分范围时才会拦截NaN。由于与NaN的比较恒为假，一个NaN基准分使同案例全部变体判定为不违规，最终报告 `risk = LOW`、`violation_rate = 0`——在损坏数据上输出「安全」，与失败关闭原则正好相反。
2. **超出t表范围后改用正态近似。** `_conservative_critical_value` 自称返回保守95% t 值，但自由度超过30时返回1.96。真实t值在该区间仍大于1.96，区间因此被收窄，本应标记为「临界」的判定会显示为确定结论。`--repeats` 允许到100，该路径可达。
3. **布尔值被当作分数。** `_parse_score_content` 直接 `float(payload["score"])`，模型返回 `{"score": true}` 被静默记为1.0分、`false` 记为0.0分，并写入客户评分CSV。`scoring._validate_provider_score` 中已有 `isinstance(result.score, bool)` 拒绝分支，但转换发生在更早一步，该分支永远不可达——说明拒绝布尔值本就是原设计意图。
4. **证据等级断言为空。** Markdown报告含有一句同时列出三个等级名的静态说明，因此 `assertIn("演示级", 全文)` 恒为真。该断言无法区分任何等级，变异测试中把5例边界改为2例未被发现。

### 修复

- `audit_records` 在任何比较之前拒绝非有限分数，与 `io.load_score_records` 的既有检查对齐；
- 自由度超出列表范围后返回表中最保守的t值，而不是正态近似；
- 评分解析在转换前拒绝布尔值，使 `scoring` 中原有的拒绝意图真正生效；
- 证据等级断言改为定位「证据强度」所在行与HTML卡片元素，不再匹配全文。

### 新增验证手段

- 属性测试独立重演已公布公式，对随机配置与随机分数交叉检验效度余量和违规计数；
- 三类判定新增阈值边界测试，固定「落在阈值上不算违规」的语义；
- 失败关闭测试覆盖配置、记录与两个CSV加载器此前从未执行过的拒绝分支；
- 评分适配器新增代码块、夹杂散文、非JSON、数组、缺失字段、越界、非字符串理由、非本机HTTP与URL内嵌凭据的测试；
- `scripts/coverage_report.py` 以标准库 `trace` 实现逐模块行覆盖棘轮，接入 `review.ps1` 与CI。

### 验证

- 108项自动化测试通过，行覆盖率由此前未测量提升至86.9%，`report` 与 `html_report` 达到100%；
- 15个变异体全部被测试捕获，其中包括三处修复的回归变异、三类阈值边界、效度余量定义、风险等级触发条件与证据等级边界；
- 变异测试初次运行受Windows时间戳精度与 `__pycache__` 影响出现假阳性，改为 `-B` 并禁止写入字节码后重做；
- 覆盖率门禁自身完成红绿验证：提高下限与引用不存在的模块均使其退出码为1；
- 3000次随机试验中实现与独立推导的效度余量、违规计数完全一致。

## 审查门J：变异测试与比较器拒绝面

审查门I建立了正确性要求，但当时的验证仍依赖一次性脚本。本轮把手段固化，并用它复查已有测试的有效性。

### 发现

1. **主规则无测试。** `scripts/mutation_check.py` 首次运行即暴露：删除 `_risk_level` 中「效度余量小于等于0」的判据后，全部测试依然通过。这是README的招牌规则——评分器对表面修改的奖励不低于它对内容退化的识别——却没有任何用例在违规率低于50%时验证它单独生效。
2. **断言与名称不符。** 一个用例名为「正边距时不应为HIGH」，实际断言 `risk_level == "HIGH"`，注释写「三分之一违规」而真实违规率为三分之二。误导性的测试名会造成错误的覆盖感。
3. **假值陷阱。** 新写的用例用 `result.mean_validity_margin or 1.0` 取值，效度余量恰为 `0.0` 时被当作缺失。边距为0正是该规则的临界情形，这个写法会让测试在最关键的点上失效。
4. **比较器拒绝面未测。** `comparison.py` 约54行未执行，全部是Gate 6依赖的拒绝分支：上下文不一致、阈值不一致、变体集合不一致、字段类型错误与汇总数字被篡改。

### 修复

- 补充效度余量风险规则的三个用例，分别覆盖边距为0、高违规率与全部通过；
- 重命名并改写误导性用例，明确它验证的是两个HIGH触发条件相互独立；
- 用显式的 `None` 判断替代假值兜底；
- 新增47个比较器拒绝用例，覆盖上下文、配置、身份、字段类型、汇总篡改与JSON装载。

### 新增门禁

- `scripts/mutation_check.py` 登记20个可能真实发生的缺陷，逐个注入并运行完整测试；
- 每个子进程使用 `-B` 且禁止写入字节码，避免同字节长度的变异在粗粒度时间戳下命中旧 `.pyc`；
- 运行结束后按SHA-256核对全部源文件已还原，未还原则以退出码2报错；
- 变异体锚点不唯一时直接失败，防止代码变动后门禁悄悄失效；
- 门禁接入 `release_check.ps1` 与CI；本地 `review.ps1` 保持快速，只执行编译、测试、覆盖率与离线演示。

### 验证

- 158项自动化测试通过；20个变异体全部被捕获，运行约40秒；
- `comparison` 行覆盖率由88.0%升至99.3%，整体由86.9%升至89.2%；
- 本轮除版本号外未改动 `agent_audit` 任何生产逻辑，说明缺口全部在测试侧；
- 比较器用例的载荷经JSON往返构造，与CLI实际传入的形状一致，而不是dataclass转换留下的元组。

## 审查门K：拒绝面收口与测试速度

审查门J把变异测试变成门禁，本轮用同一套方法把剩余的失败关闭面补完，并处理它带来的成本。

### 发现

1. **凭错误原因通过的测试。** 一个用例声称验证「检查点含有本次运行之外的样本会被拒绝」，实际触发的是上下文哈希不一致。真正的越界检查从未被执行过。构造正确场景需要保留头部哈希、只在样本区混入外来记录——也就是被篡改而非被换掉的检查点。
2. **测试套件变慢3.5倍。** 新增的未联通端点用例单独耗时6.07秒：三次尝试各等满2秒超时，因为操作系统并不总是对未监听的回环端口直接拒绝。变异门禁要跑27遍，这个代价会被放大。
3. **传输层从未被执行。** 重试判断、退避、终态错误与缺失回复体共42行代码没有任何测试，而这正是网络条件下最容易出错的部分。

### 修复

- 用被篡改的检查点构造真实越界场景，并把原用例改名为它实际验证的「不同案例集导致上下文不一致」；
- 把未联通端点的超时降到0.25秒，保留重试次数断言，套件恢复到3.5秒；
- 以脚本化失败的本地HTTP服务覆盖传输层，退避用 `unittest.mock` 替换以免真实等待。

### 新增覆盖

- 检查点：创建冲突、缺失、空文件、空行、非对象行、头部缺失或类型错误、schema不支持、上下文不一致、重复样本、逐字段样本校验、末尾截断的定位与修复；
- 传输层：七个可重试状态码逐个验证、401不重试、重试耗尽、非JSON响应、缺失 `choices[0].message.content`、用量缺失、连接被拒；
- CLI：三个子命令的装配与默认值、错误以用法错误退出而非堆栈、评分清单的哈希、记录数、模型、重复次数、温度与量表校验；
- `run_scoring`：全部参数校验与评分器返回值校验。

### 验证

- 275项自动化测试通过，耗时3.5秒；
- 27个变异体全部被捕获，新增检查点上下文、重复样本、清单记录数、CSV有限性与重试判断等拒绝面；

- 覆盖率棘轮同步上调，整体下限由86.5%提高到99.0%；
- 本轮除版本号外未改动 `agent_audit` 任何生产逻辑。

## 审查门L：CI与本地测量的分歧

前三个版本的本地门禁全部通过，但远端CI从v0.8.0起连续六次失败。本轮记录这次分歧的根因，以及使它长期隐藏的流程缺口。

### 根因

`scripts/coverage_report.py` 原先调用 `python -m trace --ignore-dir=<stdlib>`。`trace` 用 `_Ignore.names()` 决定是否记录某个文件，而该判断以**文件基名**为缓存键：

- 标准库的 `io.py` 位于被忽略的目录，首次询问后缓存写入 `{"io": 1}`；
- 我们的 `agent_audit/io.py` 基名同样是 `io`，直接命中该缓存，被一并忽略；
- 谁先被询问取决于平台与执行顺序，因此同一条命令在Windows报告10个模块、在Linux只报告9个。

本地复现证实了该机制：先问标准库的 `io.py` 时，我们的 `io.py` 被判定忽略；先问我们的则不会。这也意味着当初设定门槛那天若顺序相反，`io` 会被设成一个恒不触发的下限并长期无人察觉。

CI日志同时暴露第二个问题：`checkpoint` 在Python 3.10上为83.1%，本地3.12为83.7%。不同解释器对哪些行携带字节码的判断相差一两行，而当时的门槛只留了0.5个点余量。

### 修复

- 覆盖率工具直接驱动 `trace.Trace`，并把 `ignore` 替换为只看绝对路径的判断，彻底脱离模块名与 `.cover` 文件命名；
- 修正测试发现位于追踪区域之外的问题，否则模块级代码与全部 `def` 行不会被计入；新旧实现在同一解释器上得出逐模块完全一致的数字，构成交叉验证；
- 逐模块门槛由百分比改为未覆盖行数上限，避免把跨版本的一两行差异按模块大小放大；
- 门禁新增两条与数值无关的不变量：任何模块零记录即失败，任何模块缺少预算即失败——真正抓住本次缺陷的正是这类不变量，而不是精确百分比。

### 流程缺口

更根本的问题是：v0.8.0、v0.8.1、v0.8.2 连续三次推送，都只依据本地门禁就宣布完成，从未读取远端CI。发布规范此前也只要求核对提交哈希。现已在发布检查中增加第10步，要求推送后逐次确认CI在全部受支持版本上通过。

### 验证

- 286项自动化测试通过；
- 新增覆盖率工具自身的测试，并完成红绿验证：把判断改回按模块名后，四项测试失败，其中包括精确复现该缺陷的用例与顺序无关性用例；
- 门禁自身红绿验证：预算过小与模块缺少预算都会使其退出码为1；
- 补上 `python -m agent_audit` 入口测试，该入口写在README中却从未被执行；
- 本轮除版本号外未改动 `agent_audit` 任何生产逻辑。

### 校准结果（v0.8.4）

修复后读取CI实测数据，三套环境的逐模块未覆盖行数完全一致：

| 环境 | `io` 是否出现 | 未覆盖行数 | `audit` 覆盖率 |
|---|---|---:|---:|
| Windows / Python 3.12（本地） | 是 | 14 | 99.3% |
| Ubuntu / Python 3.12（CI） | 是 | 14 | 99.3% |
| Ubuntu / Python 3.10（CI） | 是 | 14 | 99.2% |

行数跨解释器完全稳定，百分比相差0.1个点。这实证了把逐模块门槛由百分比改为行数上限的判断，预算据此由「实测值加2行」收紧为「实测值加1行」。

## 审查门M：模型辅助改写的边界与变异门自身的可靠性

本轮引入项目第二条外发链路（把客户原文交给模型改写），并在收尾时发现变异门自己有一处会污染工作区的缺陷。

### 设计风险

等义改写是目前唯一持续暴露评分器失效的变体类型（四轮真实运行合计：改写 7/17 违规，作弊 0/17），而抓到这些失效的是整句重写，不是换连接词。自动产出那种强度的改写只有模型或人。由此带来三个风险：

1. **循环论证**：生成器与评分器同源时，「什么算等义」由被测系统自己定义；
2. **等义无法机器证明**：规则改写有精确后置条件（剥离连接词后两串完全相等），模型改写没有任何等价物；
3. **客户原文外发**：这是继评分之后的第二条外发链路。

第 2 点决定了姿态：**模型起草，人工批准**。工具绝不为一个它无法验证的等义声明背书。

### 实测推翻的判断

原本打算把「基准里有而改写里没有的数字」和「否定词计数变化」做成硬拦。在本仓库五个人工撰写的真·等义改写上实测，它们拦下了 2 个：

- `school_start`：基准「睡眠**不**足」与改写「缺乏睡眠」是同义词，一个含否定字一个不含；
- `campus_phones`：所谓「丢失的数字『一』」其实是「统**一**收纳」里的一。中文没有词边界，数字字符大量出现在普通词中。

40% 的误拦率会训练审阅者直接忽略 `status` 列，比没有检查更糟，因此两项降级为 `review_notes`。该测量以回归测试固化：任何人工改写被硬拦即失败，同时另有一项测试确认这两个检查是被降级而不是被删除。

### 我在自己新写的代码里发现的两个缺陷

合并批准行的那段代码写完后复读，发现：

- 追加分支用的是生成器的 `run.rows` 而不是含批准行的 `rows`，**批准的改写会被整体丢掉**；
- 重复执行同一条合并命令会产生重复行。

重写为：先合并、再按 `(case_id, variant_id)` 去重追加批准行、并在存在批准行时强制 `set_origin = "mixed"`。三条行为各有对应测试与变异体。

### 变异门自身的数据破坏

一次 Windows 运行在恢复被变异的模块时抛出 `OSError: [Errno 22]`。该写入位于 `finally` 中，异常越过了其后的「是否已全部恢复」检查，进程带着仍被变异的 `agent_audit/scoring.py` 崩溃退出——正是那道检查本该防住的结果。修复：

- 所有写入改走带重试且不抛出的 `write_source`，以返回值报告失败；
- 恢复校验无条件执行，失败时逐个打印 `git checkout -- <path>`；
- 为该脚本补测试，覆盖正常写入、可恢复的瞬时失败、以及放弃重试的上限。

### 一个被顺带发现的隐性失效

用 `Path.write_text` 批量改写源文件时，Windows 下默认把 `\n` 翻成 `\r\n`。变异门按字节匹配锚点，被改成 CRLF 的 `html_report.py` 中全部锚点随即失配。这次它以「锚点过期」的形式大声报错，但同样的机制也可能让某个变异体静默失效。已补一条行尾不变量测试：`agent_audit`、`tests`、`scripts` 下的 `.py` 与 `.ps1` 不得含 CRLF。CSV 明确排除——`csv.writer` 按 RFC 4180 用 CRLF 结束行，那是正确的。

### 验证

- 533 项自动化测试通过；
- 60 个变异体全部被捕获，其中 13 个为本轮新增，覆盖批准/拒绝分流、基准哈希校验、`status` 取值校验、来源标记、去重、循环论证拒绝、起草模型缺失拒绝与矛盾的来源声明拒绝；
- 提示词约束以测试固化：评分标准与用途说明都不得出现在发往供应商的消息里。
